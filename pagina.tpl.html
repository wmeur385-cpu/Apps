É um cliente só.

    O Serena dá ao agente um "IDE" para código: achar o símbolo, achar quem o referencia, ver a estrutura. Funciona porque o código já tem um language server que sabe o que cada coisa é. Os dados de uma empresa não têm. Esta camada constrói isso para entidades de negócio: junta o mesmo cliente espalhado em seis fontes que discordam, data cada afirmação e cita a linha de onde ela veio.

    Dados 100% fictícios, gerados por script com semente fixa. A camada roda agora, no seu navegador, sobre os arquivos crus embutidos nesta página. Nada foi pré-calculado.

        Calibração com planejamento de experimentos

        A camada tem uma dúzia de limiares e algumas regras. Em vez de ajustar no olho, rodei a sequência clássica: matriz ortogonal de Taguchi para descobrir o que importa, superfície de resposta para modelar, e um otimizador bayesiano para o ajuste fino. A resposta principal é o erro silencioso: menção ligada ao cliente errado ou cadastro juntado à entidade errada. Pendência não conta como erro, porque fica visível para uma pessoa decidir.

          O que um cliente novo cobra antes da primeira resposta

          A camada responde. Implantar num cliente de verdade cobra três coisas antes disso: saber em que estado os dados estão, garantir que cada pessoa só vê o que já vê, e ter uma régua para medir qualquer sistema com as mesmas perguntas.

          1. Laudo de saúde dos dados, em segundos

          node laudo.js <pasta> lê qualquer pasta de exportações (CSV com qualquer separador, JSON, JSON por linha, texto) sem conhecer o esquema: tipa cada coluna pelo conteúdo e não pelo nome, descobre o que liga com o quê, aponta cópias entre sistemas e lista os riscos do maior para o menor. É o que um engenheiro residente levanta na primeira semana. Testado contra uma contagem independente, contra a mesma base com nomes de coluna trocados, separador trocado e três máscaras de CNPJ misturadas, e contra sabotagem plantada: 27 checagens, rodadas 3 vezes.           2. Cada pessoa só vê o que já vê

          Cinco perfis (comercial, financeiro, jurídico, suporte, auditoria), cada um com as fontes que já enxerga no sistema de origem. A identidade da entidade é recalculada só com o que o perfil vê; o dossiê diz quantos registros ficaram ocultos, nunca o que dizem. O teste é um ataque pré-registrado (critérios escritos antes de rodar, hash ): em checagens, tokens que só existem em fontes proibidas foram procurados em todas as saídas de todas as ferramentas, com violações. No caminho, o ataque pegou uma falha real: menções pendentes não eram filtradas por perfil. Está corrigida e virou armadilha documentada em AGENTS.md.

          O cliente selecionado acima, , visto por cada perfil. Troque de cliente na busca e a tabela acompanha.

          Repare quando dois perfis recebem endereços diferentes: cada um está certo dentro do que pode ver, e a coluna "oculto" avisa que falta algo. Limite: a permissão é por fonte, como nos sistemas de origem. Permissão por linha (o vendedor só vê os clientes dele) não está implementada.

          3. Uma régua para qualquer Company Brain

          A pasta bancada/ transforma o benchmark numa bancada aberta: mesmos dados, mesmas perguntas, mesmo critério, qualquer sistema. Um adaptador de três funções (preparar, responder, nome) liga o sistema, inclusive por HTTP. Ela mede evidência completa, tokens, acerto sem modelo, ambíguas sem aviso e seis armadilhas plantadas (cliente que não existe; matriz e filial sem a cidade), e devolve faixa sobre várias bases, não número único. Um teste prova que a bancada reproduz o benchmark desta página na semente de desenvolvimento.

          O piso "pega" a armadilha do cliente inexistente só porque não devolve nada: armadilha se lê junto com evidência. A bancada vê a resposta, não a entidade; acerto por coincidência na entidade errada conta aqui e não no benchmark interno (diferença de 2 em 420 na semente de desenvolvimento).

          Limites desta prova

          • Os dados são sintéticos. Quem escreveu o gerador também escreveu a camada, por isso o gerador vai junto e o teste fora da amostra existe. Dado real de uma empresa vai ter bagunça que eu não imaginei.
          • Uma entidade só (cliente) e seis fontes. Não tem produto, pessoa, pedido nem relação entre eles além de matriz e filial.
          • A permissão é por fonte e por perfil, como nos sistemas de origem desta base. Permissão por linha, por campo ou por hierarquia não existe aqui, e numa empresa de verdade ela existe.
          • São 4,5 mil registros. A junção por nome dentro da mesma cidade compara pares; com milhões de registros ela precisa de bloqueio por token antes.
          • A linha de base é busca por palavra-chave. Busca vetorial lidaria melhor com erro de digitação, mas continuaria sem fazer junção entre fontes nem saber qual versão é a mais recente. Não testei.
          • Ainda falta a etapa com modelo: um Haiku respondendo às mesmas perguntas com cada contexto, contando acerto e tokens cobrados de verdade. O script está pronto (avaliar_llm.js) e pede confirmação antes de gastar.

          Como rodar

          Um núcleo em JavaScript puro, sem dependências, é o mesmo arquivo que roda nesta página, no servidor MCP e no benchmark.

          node gerar_dados.js          # base fictícia (semente 20261002)
node testes.js               # 12 testes, inclusive o MCP de ponta a ponta
node benchmark.js 20         # tabela acima
./fora_da_amostra.sh         # 10 sementes novas
node avaliar_llm.js          # mesmo teste com um modelo barato respondendo

          Para ligar no Claude Code ou em qualquer cliente MCP:

          { "mcpServers": { "dossie-entidades": { "command": "node", "args": ["/caminho/servidor_mcp.js"] } } }
